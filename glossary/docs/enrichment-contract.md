# Additional glossary materials (workflow v2)

New `request.json` files contain `workflow_version: 2`; jobs with `humanization_required: true` additionally get a humanization pass. Older published jobs stay on the previous contract. These materials enrich the full plan and the article; they do not set a limit on length or on the number of sections.

## Research and evidence

- `research.md`: each finding starts with `### R-01` and contains an independent source, the exact fragment or location, the verification date, the jurisdiction/limitation, the reader's question, the practical benefit and a potential section. The brief agent does this itself; a separate researcher is needed only for a complex term.
- `brief.md` and `serp.hybrid_outline.md`: the brief records whether the term is narrow or covers several meanings, processes and decisions. For a broad term the hybrid outline also records the reader tasks found through targeted questions and independent sources beyond the exact SERP, and the reasons for including or excluding them. The three market SERPs for the exact query remain a separate, unchanged stage; additional queries are not passed off as their results. Useful additions get a place in the structure and in the writer's content assignments, and the facts go through independent verification.
- `sections.json`: the top-level `information_gain` contains at least one object of the form `{"section_id":"decision","research_ref":"R-01","reader_value":"What the reader can decide"}`. The full H2–H4 structure is kept.
- `evidence.md`: each verified claim has a heading `### Claim TAX-01`, the fields `URL`, `Verdict: supports|partial|unsupported`, scope of application, and `Article link: required|optional|forbidden` with a reason. Key legal/tax claims and the main additional value get `required`. The script checks that these URLs are present in the finished text; the editor and QA judge whether the link makes sense in context.

## Visuals

`visuals.json` holds a `visuals` list; an empty list requires a concrete `omission_reason` describing the visual tasks that were considered. A zero-visual plan is a normal choice; there is no norm or ceiling for the number of useful visuals. Each candidate is judged against its own task: does it explain a sequence, a fork, a relationship or a scale better than what is already presented. A table, a list or text may sit next to a diagram; their mere presence is not a reason to reject it. If one shared diagram for several jurisdictions is misleading, separate diagrams with an explicitly stated scope of application are considered first. Do not duplicate information just to have more formats. When planning, use the bar/line/process/decision schema from `../blog/docs/blog-workflow-v2.md`: `id`, `type`, `section_id`, `purpose`, `title`, `alt`, `caption`, `sources`, `data`; every numeric point or node has the ID of a verified claim. The renderer adds the local PNG and hashes; the uploader adds the verified source HTTPS URL and the Strapi media ID. In `edited.md`, before binding, each planned `[[VISUAL:id]]` is replaced with a real Markdown image, a `Caption:` line and links to the public primary sources of the visual. QA checks each exact block, the image visually, the data, the caption, the facts, the URLs and that the hashes match. The cover stays on the separate glossary template, as before.

Order: plan → `materials-check --stage inputs` → writing/editing → `render-visuals` → visual check → `upload-visuals --dry-run` → after Strapi writing is permitted, `upload-visuals` → `bind-visuals` → final humanization pass → QA. If there are no visuals, the final pass goes right after the main editing. Media upload writes to production Strapi; the earlier rule of an explicit request for writing is kept. The renderer and the uploader reuse the blog V2 code at the neighbouring path, so that the image schema stays shared. The Google Docs V2 exporter is used only when a visual is present. The agreement on a separate glossary cover does not change.

## Expert comment

`expert_quotes.json`: `{"version":1,"quotes":[],"omission_reason":"No first-person insight would improve this definition."}`. When a comment is present, its object has `id`, `section_id`, `speaker` (the author's/editor's username), `attribution` (the exact Strapi `name` field), `text`, `source_type` (`verbatim` or `editorial_draft`), `source` for a verbatim quote, `evidence_ids`, `status` (`proposed`, `approved`, `rejected`). The snapshot of CMS names is saved in `raw/speaker-profiles.json` via `scripts/fetch_speaker_profiles.py`. The writer inserts the exact text and attribution as a quote block. An editorial draft is marked in the Google Doc as a suggestion. `approve-comment` records the person, the source of the explicit approval, the time and the hash of the words/attribution. Changing the words resets the approval and blocks the CMS; a rejected comment is removed from the article. An expert's opinion does not replace a primary source for a fact.

## Checks and Google Doc

For a job with `humanization_required: true`, the same editor, in a separate final pass, reads the whole current `edited.md` against the local `.agents/skills/humanizer/SKILL.md`: headings, tables, lists, captions and repeating constructions. The editor writes an English-language `humanization_report.md` with the exact lines `Scope: whole page` and `edited.md SHA256: <sha256>`, "before → after" examples or a justification for the absence of edits, a check that the meaning is preserved, and open questions. Protected visual blocks and verbatim expert comments are not rewritten. After any change to the text, the editor updates the report and its hash. The AI-Score, if given, serves as a subjective editorial diagnostic, not as an estimate of the probability of authorship or as an admission criterion. QA assesses the text and the report independently.

`materials-check --stage inputs` checks the links between R-IDs, claim IDs, sections, manifests and the profile snapshot. `--stage qa` adds checks of the bound image, hashes, URLs, caption, exact comment blocks and mandatory links, and, for jobs with `humanization_required: true`, the presence and freshness of the humanization report. The QA report includes all `fingerprint` lines, including the hash of `humanization_report.md` for jobs with `humanization_required: true`; packaging is blocked if the materials change after PASS. `--stage cms` blocks an unapproved comment and a stale report.

When a visual is present, the Google Doc is created through the shared blog V2 exporter as a native inline image. `review/NN-document.json` stores the document and image IDs; `verify_gdoc_review.py` checks the IDs, order, URLs, text, headings and the configured glossary review folder. The PDF is then reviewed by eye, as before. For a text-only article the earlier HTML import remains.
