# Example Co glossary term

Read the project `AGENTS.md`, `docs/design-notes.md`, and this skill. The parent agent owns orchestration and deterministic checks. Specialist agents own research, evidence, prose, editing, and QA. All article-facing artifacts are in English.

## Start a job

Create an isolated folder under `jobs/` with `python3 scripts/glossary_job.py new --term "<term>" --slug <slug> --date YYYY-MM-DD --author <Strapi username>`. The job records the default editor `jane.doe`; record the term's topic-sheet row. Check the live glossary and relevant blog pages for overlap and check that the candidate slug is free; the public API cannot establish that a draft slug is free. Use existing related URLs only, and do not treat a planned term as a live link.

After selecting a topic-sheet row, save its `temnik_cluster_id`, `temnik_row`, and exact `primary_query` in `request.json`. Preview `python3 scripts/glossary_temnik.py start --job <job> --date YYYY-MM-DD`; when the batch is actually launched, add `--apply` to set `Action=new`, `Status=in progress`, and the start date. The command checks the row ID, slug, locale, and current cell values before writing. Serialize these shared-sheet updates across jobs.

## Route specialists

For XMLRiver primary SERPs, use `config/glossary-serp-geos.json`. The country and domain are separate parameters. Record both settings and the returned market evidence in `serp.results.md`.

Use depth-1 Codex subagents from the role files in `agents-src/agents/`. Spawn with `fork_turns="none"`; pass the job path, the role-file path, and the assigned task. Use `config/codex-model-routing.json` for Codex roles when model overrides are available. New jobs record `writer_backend` in `request.json` at creation and default to MiniMax via OpenRouter. Existing jobs without the field use their Codex writer. Keep one writer per term and all sources and outputs in the job folder. Give the writer the heading contract or exact rework defect without a word budget, a short-form request, or parent-authored prose.

1. `glossary-brief` captures the exact English term as the primary query in three market-targeted English-language SERPs: US, UK, and DE. It records each market's observed organic results separately in `serp.results.md` (up to the first ten available), including query, tool, date, confirmed market/language, URLs, relevance, and supplied positions; it never invents market targeting or rank. If a market is unavailable, it tries another market-aware source and reports the unresolved gap before the brief proceeds. It opens relevant unique glossary/explainer pages across all three markets and records their market provenance, H1–H4 hierarchy, substantive questions, and skip/access reasons in `serp.competitor_structures.md`. Shared URLs are inspected once but retain all observed markets. The agent compares markets and synthesizes `serp.hybrid_outline.md` as the coverage-maximal union of useful questions, examples, distinctions, and subtopics across those pages. It keeps a useful unique item even if only one competitor or market has it, merges true duplicates, and removes only irrelevant or promotional material; useful coverage is never removed for compactness. Before finalizing that map, it checks whether the exact-term results miss reader tasks, especially for a broad term, several meanings, or a term used in more than one workflow. When needed, it uses targeted task questions, relevant primary guidance, and existing related pages to find useful decisions or examples, records what was considered and why it belongs or falls outside the entry, and maps accepted items into the hybrid and brief. These discovery checks do not replace or relabel the three primary-query SERPs. Jurisdiction-specific rules stay scoped. Independent research beyond the SERP identifies at least one concrete information-gain item absent from the relevant top pages, supported by an independent source they do not cite, and explains the reader decision it helps. Without such an item the brief is blocked. The full H2–H4 hierarchy goes into `brief.md` and `sections.json`. For each writer unit, `brief.md` adds a short content contract covering the reader question, necessary distinction or mechanism, useful example or decision, and evidence lead or gap; every useful hybrid item maps to a contract. These contracts specify substance without paragraph counts, short-form instructions, word budgets, or prose recipes. The parent checks that all three market result sets and SERP artifacts exist, the reader-task scope check is recorded, useful items survive in the full outline and content contracts, and the information-gain item has a research lead. After evidence review, it proceeds to writing without a publisher approval pause.
2. `glossary-evidence` is required for **every term**. It independently opens current primary sources for the full outline, its examples, and the planned information-gain item, then writes `evidence.md` with claim, source URL, support, date checked, and verdict. Unsupported or jurisdiction-specific generalizations are excluded or flagged. The writer receives only verified facts from this file. An unsupported information-gain item returns to the brief agent for a defensible replacement or a reported gap.
3. The writer follows `agents-src/agents/glossary-section-writer.md` and `../blog/knowledge/writer-style.md`, in `sections.json` order. A unit is a complete H2 without H3s or one direct H3 with its H4 subtree. The first H3 turn writes the H2 heading and lead. The writer develops each brief contract and mapped hybrid point fully, including useful distinctions, mechanisms, examples and decisions supported by evidence. The definition stays in `meta.json`. For `writer_backend: openrouter` use the commands below. For the Codex writer, dispatch one unit at a time to the same thread and wait for each result.
4. Assemble the sections with `python3 scripts/glossary_job.py assemble --job <job>`, which also writes the identical `out/draft.md` expected by the blog's editor report. `glossary-editor` uses this project's `.agents/skills/humanizer/SKILL.md` and diagnoses actual defects and edits into `edited.md` while preserving useful depth, examples, distinctions, and the information-gain item. It records substantive gaps for the same writer instead of shortening around them, and lists any cut evidence-backed facts in `editor_issues.md`. Run `python3 ../blog/scripts/article_delta.py editor-report --job <absolute-job-path>` after editing; its before/after counts and hierarchy check are QA diagnostics, never a word-count gate. For new jobs with `humanization_required: true`, route a separate final whole-page humanization pass to the **same editor thread** after visual binding (or after the first edit if there are no visuals). The editor checks the current complete `edited.md`, every heading and repeated page patterns, changes only diagnosed defects, and saves `humanization_report.md` with the final text SHA-256. This pass does not replace independent QA. Rerun `editor-report` if the final pass changes `edited.md`, so its delta describes the version sent to QA. `glossary-qa` maps each useful hybrid item and any overlooked useful competitor item to the exact body passage, then checks whether that passage explains the promised question, example, mechanism, or decision rather than merely naming it. It checks factual entailment, information gain, editor cuts, brand rules, and CMS contract, writing `qa_report.md` with `Verdict: PASS` or `Verdict: BLOCK`. Underdeveloped useful coverage blocks QA without imposing a word target.
5. Route a BLOCK to the original writer or editor with the exact defect. For a MiniMax writing repair, use the command below and have the editor review and merge the candidate. After any prose change in a job requiring humanization, return the changed copy to the same editor for an affected recheck and refreshed report hash before asking the original QA thread to recheck it. If structure or unaffected sections change, run full QA again. The parent does not write article prose or mark its own work as QA.

Do not impose a word target or ceiling, mandatory FAQ, Key Takeaways, vendor comparison, or promotional CTA. A table or heading level exists when it helps the reader navigate real substance. Full coverage and useful depth determine the structure and length. Treat Example Co as an owned educational voice; product naming and the limits on statements about it are in `knowledge/positioning.md`. Read it before the brief and QA.

## MiniMax writer

After the inputs stage passes, preview `python3 scripts/glossary_writer.py write --job <job>`. It lists the exact writer units and current article budget. For a requested writing job run the same command with `--execute`. It sends one heading unit per completion with the verified packet and the previous units, saves the API receipts under `writer-api/`, then writes the standard `sections/*.md` files for `glossary_job.py assemble`. The original metadata stays in place. `python3 scripts/glossary_writer.py preflight` checks the catalogue route and glossary key without creating a completion.

For a returned writing defect run `python3 scripts/glossary_writer.py repair --job <job> --unit <unit-id> --feedback "<exact verified defect>" --execute`. Use the unit ID from the write preview. The command creates a candidate under `writer-api/repairs/` for the same editor. The current article is kept intact until the editor merges the correction. If the writer stops, read the error and saved receipts. Re-running an unchanged draft reuses completed calls. Use `--retry-failed` only for a reviewed accounted failure. Report an unavailable pinned route or an unresolved charge before making another paid request.

## Package and review

After QA PASS, run `python3 scripts/glossary_job.py package --job <job>`. This validates `term`, slug, `definition` (≤300 characters), `metaTitle` (≤70), `metaDescription` (≤200), the exact H2 sequence, and the HTML against the Strapi sanitizer. It writes `out/strapi-payload.json`, `out/content.html`, and `out/review.md`. `term` supplies H1; `definition` precedes the body on the site; `contentHtml` begins with H2. Never send the derived public `content` field.

Create a Google Doc from `out/review.md` with `python3 scripts/gdoc_review.py --job <job> --round 1 --apply`. It uses the folder configured by `config/google-drive.json` and saves the URL in `review/01-url.txt`. Run `python3 scripts/verify_gdoc_review.py --job <job> --round 1 --pdf-out /tmp/<slug>-review.pdf` to check the glossary folder, imported H1–H3 order, and full text against the packaged copy; then inspect the PDF for broken headings or paragraph orphans and adjust document layout if needed. Record the metadata, ready date, Doc URL, and `in review` status with `python3 scripts/glossary_temnik.py review --job <job> --date YYYY-MM-DD --apply`. On later rounds, preserve the sent copy and record changes and comments in `review/`. Only a reviewed version may become the CMS payload. Use the glossary folder configured in `config/google-drive.json`, not the blog flow's per-article review folders.

Prepare a distinct glossary cover before CMS submission. Use the existing glossary design reproduced by `tools/covers/render-glossary-cover.mjs`: a 1200×800 WebP with the “What is” kicker, a highlighted term label in the brand accent colour, a dark background, and the site logo. Run `npm ci --prefix tools/covers` once, then `node tools/covers/render-glossary-cover.mjs --term="<term>" --out=<job>/out/cover.webp`. Inspect the image visually and confirm the full term fits. The blog cover style is not the glossary template.

After the publisher requests a Strapi action, inspect the final payload and cover, check the published slug and project job records for duplicates, then run `python3 scripts/strapi_glossary.py dry-run --job <job>` and `create-draft`. The job's `request.json` must name the author and editor by Strapi username; use the blog's current user-ID mapping, with `jane.doe` as editor, and verify both populated people on the public record. The glossary collection `find` and `findBySlug` force published-only results even for authenticated requests, so they cannot prove a draft slug is free; Strapi's UID validation is the final check on creation. Inspect the create response and local draft record, then run `attach-cover` before publication. Publish only on an explicit publication request, using the script's `publish` command. Run `verify` and inspect the public API and cover URL. When the production site renders the page, check the rendered production URL, headings, metadata, definition, cover, author, and editor; otherwise the publisher checks the rendered page on a staging site and reports the result. Record verification in the job's publication log, then preview and apply `python3 scripts/glossary_temnik.py publish --job <job> --date YYYY-MM-DD --apply` to save the publication status, URL, and date. An unpublished draft cannot be tested on a public site page because the glossary API exposes only published entries.

After the verified live publication and topic-sheet update, preview `python3 scripts/indexnow_glossary.py --job <job>` and run `python3 scripts/indexnow_glossary.py --job <job> --apply` to notify IndexNow. The command checks Example Co's own public key file, sends only the published glossary URL, and saves a dated HTTP receipt in the job's `indexnow/` folder. Record the receipt path and accepted HTTP status in `publication.md`; report any failure without claiming submission. For a one-time backfill of all published glossary articles, use `--all` instead of `--job`. It takes URLs from the live glossary sitemap, excludes the section index, and stores receipts under `docs/indexnow/`.

## Related content

Apply the selection and review rules in `docs/related-content/policy.md` to **both** `relatedTerms` and `relatedArticles`. Refresh the live catalog with `python3 scripts/glossary_related_inventory.py --out <inventory.json>`. The brief can shortlist published destinations, but final links are chosen after reading the destination and identifying the next reader question it answers. The editor reviews usefulness and scope; independent QA checks the reason and destination. Revisit links after the whole batch is live, including useful links from older glossary pages to new ones. Record ordered destination IDs, reasons, and any empty-list reason in a reviewable relation manifest. No count is mandatory, and a blog article belongs in `relatedArticles` only when it develops an application, workflow, or comparison useful to that term's reader. A relation update is a separate Strapi write subject to the project's explicit authorization rule; use `python3 scripts/glossary_related.py preview --manifest <reviewed.json> --inventory <inventory.json>`, then `apply` after authorization, and `verify` against the public API and rendered blocks. Serialize writes across jobs.

## Parallel jobs

Several terms can run in parallel; a handful of active job folders (for example five to ten) is a workable range, and fewer is better when review capacity is the bottleneck. Stages within a job follow the dependency order above; stages across jobs can overlap. Keep one persistent writer per job and keep live threads within the limit set in `.codex/config.toml` (`max_concurrent_threads_per_session`), leaving slots for the parent, QA and rework. Queue new work when slots are occupied. Serialize mutations to shared resources such as the topic sheet, Google Drive folder creation, and Strapi; job-local files need no global lock. Report stage and blockers per job so the parent does not have to carry every article draft in its context.

## Enriched route for new jobs

`glossary_job.py new` sets `workflow_version: 2`  and `humanization_required: true`. Jobs created without this field keep the package contract they were created under; they are not retroactively forced through the new stage. For new jobs, use the existing full SERP and hybrid-outline stages, then save `research.md` with R-IDs, independent source/passages, scope and reader value. The brief agent does this for ordinary terms; invoke `glossary-research` only when complexity justifies a separate agent. Put `information_gain` items with `section_id`, `research_ref`, and `reader_value` in `sections.json`. The evidence agent independently verifies them and uses stable `### Claim ID` headings and explicit article-link decisions.

After evidence, assess each candidate in-body visual by the distinct question, mechanism, comparison, or decision it can clarify. Use `glossary-visual-planner` for useful candidates; there is no default number or ceiling. A diagram can complement a table or prose when it adds a different view, so their presence alone is not an omission reason. Avoid duplicate visuals and decorative assets. Record `visuals.json` with a specific reason for an empty list. Use the bar/line/process/decision schema and evidence IDs from the blog V2 flow. Do not add a visual to meet a quota. Render with `glossary_job.py render-visuals --job <job>`; inspect every PNG and its data. `upload-visuals --dry-run` checks the upload. The actual `upload-visuals` writes media to production Strapi and requires an explicit request authorizing that Strapi action. Reuse the blog V2 renderer/uploader; preserve each checked original PNG URL and media ID. The writer leaves each `[[VISUAL:id]]` in its assigned section; the editor preserves the markers. After verified upload, run `bind-visuals` against `edited.md` before the dedicated humanization pass and QA. For an empty manifest, no visual stage or upload is needed.

Use `glossary-expert-comments` only where a real expert insight adds a decision, qualification, or practical point. Otherwise `expert_quotes.json` has an empty list and specific `omission_reason`. For a comment, run `python3 scripts/fetch_speaker_profiles.py --job <job>` and use the exact Strapi profile name; attach verified evidence IDs for factual assertions. An editorial draft remains `proposed` in the Google Doc, with a review-only note. The comment text and attribution must match the manifest exactly. After the person explicitly approves it, run `glossary_job.py approve-comment --job <job> --id <id> --by <person> --reference <approval record>`, then repeat QA and package. Remove rejected comments from the article. CMS dry-run and creation block proposed comments.

Once `research.md`, evidence, `sections.json`, `visuals.json`, and `expert_quotes.json` exist, run `materials-check --stage inputs` before writing.

Before QA, run `materials-check --stage qa`; for jobs requiring humanization, it rejects a missing or stale whole-page report. The QA agent inspects the report, images, sources, comments and the full article independently. `fingerprint` includes research, evidence, sections, visual and comment manifests, the humanization report when required, plus the speaker profile snapshot when comments exist. Package only with a current QA PASS. If a visual exists, `gdoc_review.py` uses the blog V2 native-image exporter in the configured glossary review folder; `verify_gdoc_review.py` checks image objects, order, URLs, captions/text and headings against the sent copy and manifest. Keep the usual PDF visual inspection. Run `materials-check --stage cms` before any requested CMS action. See `docs/enrichment-contract.md` for exact artifact schemas and sequence.
